# Як працює Raycaster — пояснення до захисту

Файл: `src/Raycaster.cpp`, метод `Raycaster::render()` (рядки 17–260).
Номери рядків нижче відповідають саме цьому файлу.

---

## Загальна ідея

Гра не має справжньої тривимірної сцени. Світ — це звичайна плоска карта з символів, на яку ми ніби дивимось зверху: `1` означає стіну, `0` — вільну клітинку, `2` — двері. Щоб отримати вигляд «від першої особи», ми робимо простий трюк: для кожного вертикального стовпця екрана випускаємо з позиції гравця один промінь **по площині карти** (горизонтально, як лазерна указка, що світить уздовж підлоги) і з'ясовуємо, на якій відстані він зустріне стіну.

Далі працює правило перспективи: чим ближче стіна, тим вищою вона здається. Тому для кожного стовпця ми малюємо вертикальну смужку, висота якої обернено пропорційна відстані. Коли 800 таких смужок стоять поруч, мозок сприймає їх як тривимірний коридор.

Вертикальних променів немає зовсім — висота нічим не «трасується», вона просто обчислюється з відстані. Через це всі стіни однакової висоти, а дивитись угору чи вниз неможливо. Зате метод дуже швидкий: на кадр потрібно лише 800 променів, а не 480 000 (по одному на піксель), як у ray tracing.

Метод `render()` складається з двох частин:
1. **Стіни** — цикл по всіх стовпцях екрана (рядки 39–160).
2. **Монстри-спрайти** — проєкція ворогів на екран з урахуванням того, що їх можуть закривати стіни (рядки 162–259).

## Допоміжна функція затемнення (рядки 10–15)

```cpp
namespace {
Uint8 shadeChannel(const int value, const float factor) {
    const int scaled = static_cast<int>(static_cast<float>(value) * factor);
    return static_cast<Uint8>(std::clamp(scaled, 0, 255));
}
}
```

Ця маленька функція бере одну складову кольору (червону, зелену чи синю, від 0 до 255) і множить її на коефіцієнт яскравості. Наприклад, `shadeChannel(200, 0.5)` дасть 100 — колір удвічі темніший. `std::clamp` гарантує, що результат не вийде за межі 0…255, навіть якщо коефіцієнт більший за 1. Анонімний `namespace` означає, що функція видима лише всередині цього файлу.

## Частина 1. Стіни

### Крок 1. Налаштування камери (рядки 27–37)

```cpp
const float playerX = player.getX();
const float playerY = player.getY();
const float angle = player.getAngle();
const float fov = player.getFov();

const float dirX = std::cos(angle);
const float dirY = std::sin(angle);
const float cameraPlaneScale = std::tan(fov * 0.5F);
const float planeX = -dirY * cameraPlaneScale;
const float planeY = dirX * cameraPlaneScale;
std::vector<float> depthBuffer(static_cast<std::size_t>(screenWidth), 1.0e30F);
```

Спочатку ми забираємо в гравця його позицію, кут, куди він дивиться, і кут огляду (FOV, у нас 70°).

З кута обчислюється **вектор напрямку** `dir` — одиничний вектор, що показує, куди дивиться камера. Косинус дає складову по X, синус — по Y.

Далі будується **площина камери** `plane`. Уявіть, що перед очима гравця на відстані 1 стоїть прозоре вікно, а екран монітора — це і є це вікно. Площина камери — це вектор уздовж цього вікна, перпендикулярний до напрямку погляду. Перпендикуляр отримуємо поворотом `dir` на 90° (звідси `-dirY` і `dirX`). Довжина площини дорівнює `tan(FOV/2)`: що ширша площина, то ширший кут огляду. Для 70° це приблизно 0.7.

Наприкінці створюється **буфер глибини** `depthBuffer` — масив із 800 чисел, по одному на кожен стовпець екрана. Сюди ми записуватимемо відстань до стіни в кожному стовпці, щоб потім знати, чи не ховається монстр за стіною. Спочатку всі значення дорівнюють «нескінченності» (`1e30`). Масив створюється один раз на кадр, а не для кожного променя — це важливо для швидкодії.

### Крок 2. Напрямок променя для стовпця (рядки 39–42)

```cpp
for (int x = 0; x < screenWidth; ++x) {
    const float cameraX = (2.0F * static_cast<float>(x) / static_cast<float>(screenWidth)) - 1.0F;
    const float rayDirX = dirX + planeX * cameraX;
    const float rayDirY = dirY + planeY * cameraX;
```

Головний цикл проходить по всіх стовпцях екрана, від 0 до 799. Для кожного стовпця обчислюється `cameraX` — його положення на площині камери. Найлівіший стовпець отримує −1, центральний — 0, найправіший — майже +1.

Напрямок променя — це напрямок погляду плюс зсув уздовж площини камери. Центральний промінь іде точно туди, куди дивиться гравець; крайні промені відхиляються вліво та вправо на половину кута огляду. Разом 800 променів утворюють віяло шириною 70°.

Важливо, що промені розподілені **рівномірно по площині**, а не рівномірно по кутах. Саме це пізніше дозволяє отримати відстань без спотворення «риб'яче око».

### Крок 3. Підготовка до DDA (рядки 44–68)

```cpp
int mapX = static_cast<int>(playerX);
int mapY = static_cast<int>(playerY);

const float deltaDistX = (rayDirX == 0.0F) ? 1.0e30F : std::abs(1.0F / rayDirX);
const float deltaDistY = (rayDirY == 0.0F) ? 1.0e30F : std::abs(1.0F / rayDirY);

int stepX = 0;
int stepY = 0;
float sideDistX = 0.0F;
float sideDistY = 0.0F;

if (rayDirX < 0.0F) {
    stepX = -1;
    sideDistX = (playerX - static_cast<float>(mapX)) * deltaDistX;
} else {
    stepX = 1;
    sideDistX = (static_cast<float>(mapX + 1) - playerX) * deltaDistX;
}
if (rayDirY < 0.0F) {
    stepY = -1;
    sideDistY = (playerY - static_cast<float>(mapY)) * deltaDistY;
} else {
    stepY = 1;
    sideDistY = (static_cast<float>(mapY + 1) - playerY) * deltaDistY;
}
```

Тепер треба знайти, де промінь вперше влучить у стіну. Найпростіший спосіб — рухати точку вздовж променя дрібними кроками і щоразу перевіряти клітинку. Але це повільно, а ще промінь може «проскочити» через кут стіни між двома кроками. Тому використовується алгоритм **DDA** (Digital Differential Analyzer): промінь стрибає не на фіксовану відстань, а одразу до наступної лінії сітки. Так перевіряється рівно кожна клітинка, через яку проходить промінь, — жодна не пропускається і жодна не перевіряється двічі.

Для цього готуються кілька величин:

- `mapX`, `mapY` — номер клітинки, в якій зараз перебуває промінь. Спочатку це клітинка гравця: дробову позицію (наприклад, 1.5) відкидаємо до цілого (1).
- `deltaDistX` — яку відстань уздовж променя треба пройти, щоб перетнути одну вертикальну лінію сітки і дійти до наступної. Якщо промінь іде майже горизонтально, ця відстань близька до 1; якщо майже вертикально — дуже велика. `deltaDistY` — те саме для горизонтальних ліній. Якщо промінь іде строго вгору чи вниз (`rayDirX == 0`), він взагалі ніколи не перетне вертикальну лінію; щоб не ділити на нуль, підставляємо «нескінченність» `1e30`.
- `stepX`, `stepY` — у який бік рухатися по сітці: +1 (вправо/вниз) чи −1 (вліво/вгору). Визначається знаком напрямку променя.
- `sideDistX`, `sideDistY` — відстань від гравця до **першої** вертикальної (горизонтальної) лінії сітки. Гравець зазвичай стоїть не на лінії, а всередині клітинки, тому перший відрізок коротший за повний `deltaDist`. Наприклад, якщо гравець у точці x = 1.5 і промінь іде вправо, до лінії x = 2 лишається 0.5 клітинки, тому `sideDistX = 0.5 * deltaDistX`.

### Крок 4. Цикл DDA — пошук стіни (рядки 70–88)

```cpp
bool hit = false;
int side = 0;
char hitCell = '1';
while (!hit) {
    if (sideDistX < sideDistY) {
        sideDistX += deltaDistX;
        mapX += stepX;
        side = 0;
    } else {
        sideDistY += deltaDistY;
        mapY += stepY;
        side = 1;
    }

    hitCell = map.getCell(mapX, mapY);
    if (hitCell != '0') {
        hit = true;
    }
}
```

На кожному кроці ми порівнюємо, яка лінія сітки ближче вздовж променя — вертикальна (`sideDistX`) чи горизонтальна (`sideDistY`). Промінь «переходить» через ближчу лінію в сусідню клітинку, а відповідна відстань збільшується на один `deltaDist`, щоб указувати вже на наступну лінію.

Змінна `side` запам'ятовує, яку саме лінію ми перетнули останньою: 0 — вертикальну (тобто влучили в «східну» чи «західну» грань стіни), 1 — горизонтальну («північну» чи «південну» грань). Це знадобиться для обчислення відстані, текстури й освітлення.

Після кожного кроку перевіряємо символ у новій клітинці. Якщо це не `'0'` — тобто стіна `'1'` чи двері `'2'` — промінь зупиняється, а `hitCell` зберігає, у що саме ми влучили.

**Чому цикл ніколи не зависне?** Метод `Map::getCell` повертає `'1'` для будь-якої клітинки за межами карти (`src/Map.cpp`, рядок 28). Тож навіть якщо в карті є дірка, промінь зупиниться на її краю.

### Крок 5. Відстань до стіни без «риб'ячого ока» (рядки 90–98)

```cpp
float perpWallDist = 0.0F;
if (side == 0) {
    perpWallDist = (static_cast<float>(mapX) - playerX + static_cast<float>(1 - stepX) * 0.5F) / rayDirX;
} else {
    perpWallDist = (static_cast<float>(mapY) - playerY + static_cast<float>(1 - stepY) * 0.5F) / rayDirY;
}

perpWallDist = std::max(perpWallDist, 0.0001F);
depthBuffer[static_cast<std::size_t>(x)] = perpWallDist;
```

Тут обчислюється, наскільки далеко стіна. Розберемо формулу для `side == 0`:

- Вираз `mapX + (1 - stepX) * 0.5` — це X-координата тієї грані клітинки, в яку ми влучили. Якщо промінь ішов вправо (`stepX = 1`), він увійшов у клітинку через її ліву грань, тобто `mapX`. Якщо вліво (`stepX = −1`) — через праву, тобто `mapX + 1`.
- Віднімаючи `playerX`, отримуємо, скільки треба пройти по осі X.
- Ділячи на `rayDirX`, дізнаємося, скільки «кроків променя» це займе. Це число і є відстань.

Найцікавіше — **яку саме** відстань ми отримали. Це не довжина променя від гравця до стіни (евклідова відстань), а **перпендикулярна** відстань від площини камери до стіни, тобто глибина вздовж напрямку погляду. Так виходить тому, що напрямок кожного променя складається з `dir` (довжина 1) і зсуву вздовж площини, перпендикулярної до `dir`. Отже, вздовж напрямку погляду кожен промінь просувається рівно на 1 за «крок», і поділ на `rayDirX` дає саме глибину.

Чому це важливо? Якби ми брали справжню довжину променя, бічні промені виходили б довшими за центральний, навіть коли гравець дивиться прямо на рівну стіну. Тоді пряма стіна на екрані вигиналася б дугою — це і є ефект **«риб'яче око»** (fish-eye). У завданні лаби пропонують виправляти його множенням на `cos(rayAngle − playerAngle)`; наш код отримує правильну відстань одразу, без косинуса, завдяки площині камери. Математично це те саме.

`std::max(..., 0.0001)` захищає від ділення на нуль, якщо гравець стоїть впритул до стіни. Отриману відстань записуємо в `depthBuffer` для цього стовпця.

### Крок 6. Висота смужки стіни (рядки 99–101)

```cpp
const int lineHeight = static_cast<int>(static_cast<float>(screenHeight) / perpWallDist);
const int drawStart = std::max(0, (screenHeight - lineHeight) / 2);
const int drawEnd = std::min(screenHeight - 1, (screenHeight + lineHeight) / 2);
```

Це серце всього «3D». Висота смужки дорівнює висоті екрана, поділеній на відстань. Стіна на відстані 1 займає весь екран, на відстані 2 — половину, на відстані 4 — чверть. Це закон перспективи з подібних трикутників: видимий розмір предмета обернено пропорційний відстані до нього.

Смужка центрується по вертикалі: її верх — на `(висота − lineHeight) / 2`, низ — на `(висота + lineHeight) / 2`. Тому лінія горизонту завжди проходить посередині екрана. Якщо стіна дуже близько і смужка вища за екран, `std::max` і `std::min` обрізають її до меж вікна.

### Крок 7. Де саме промінь влучив у стіну (рядки 103–109)

```cpp
float wallX = 0.0F;
if (side == 0) {
    wallX = playerY + perpWallDist * rayDirY;
} else {
    wallX = playerX + perpWallDist * rayDirX;
}
wallX -= std::floor(wallX);
```

Щоб накласти текстуру, треба знати, в яке місце вздовж грані влучив промінь: у лівий край клітинки, у середину чи в правий край. Ми обчислюємо точку влучання (позиція гравця плюс відстань, помножена на напрямок) і беремо координату **вздовж** стіни: для вертикальної грані — Y, для горизонтальної — X. Потім відкидаємо цілу частину, і залишається число від 0 до 1. Наприклад, 0.25 означає «чверть ширини клітинки від її краю».

### Крок 8. Освітлення (рядки 111–115)

```cpp
float distanceShade = 1.0F / (1.0F + perpWallDist * perpWallDist * 0.08F);
distanceShade = std::clamp(distanceShade, 0.2F, 1.0F);
if (side == 1) {
    distanceShade *= 0.8F;
}
```

Тут обчислюється, наскільки яскравою буде ця смужка. Що далі стіна, то вона темніша — це створює відчуття глибини, ніби коридор тоне в темряві. Формула `1 / (1 + d² · 0.08)` дає 1 для близьких стін і плавно спадає з відстанню. `clamp` не дає яскравості впасти нижче 0.2, щоб далекі стіни не ставали зовсім чорними.

Останній рядок — класичний трюк з оригінального Wolfenstein 3D: грані, повернуті в один бік (`side == 1`), робимо на 20% темнішими. Через це сусідні стіни, що сходяться під кутом, мають різну яскравість, і кути між ними чітко видно — без цього все зливалося б в одну пласку поверхню.

### Крок 9. Малювання смужки з текстурою (рядки 117–132)

```cpp
SDL_Texture* wallTex = (hitCell == '2') ? doorTexture : wallTexture;
int wallTexW = 0;
int wallTexH = 0;
const bool hasWallTexture =
    (wallTex != nullptr) &&
    (SDL_QueryTexture(wallTex, nullptr, nullptr, &wallTexW, &wallTexH) == 0) &&
    wallTexW > 0 && wallTexH > 0;

if (hasWallTexture) {
    const int srcX = std::clamp(static_cast<int>(wallX * static_cast<float>(wallTexW - 1)), 0, wallTexW - 1);
    SDL_Rect src{srcX, 0, 1, wallTexH};
    SDL_Rect dst{x, drawStart, 1, std::max(1, drawEnd - drawStart + 1)};
    const Uint8 texShade = shadeChannel(255, distanceShade * lightIntensity);
    SDL_SetTextureBlendMode(wallTex, SDL_BLENDMODE_BLEND);
    SDL_SetTextureColorMod(wallTex, texShade, texShade, texShade);
    SDL_RenderCopy(renderer, wallTex, &src, &dst);
}
```

Спочатку вибираємо текстуру: якщо промінь влучив у двері (`'2'`), беремо `door.png`, інакше — `wall.png`. `SDL_QueryTexture` дізнається розміри картинки й заодно перевіряє, що вона справді завантажилась.

Далі відбувається текстурування. Значення `wallX` (від 0 до 1) перетворюється на номер стовпчика пікселів у картинці: якщо текстура завширшки 256 пікселів, а `wallX = 0.25`, беремо стовпчик номер 64. Прямокутник `src` вирізає з текстури вертикальну смужку шириною рівно 1 піксель на всю висоту картинки. Прямокутник `dst` — це місце на екрані: стовпець `x`, від `drawStart` до `drawEnd`. `SDL_RenderCopy` копіює смужку з текстури на екран і сама розтягує її до потрібної висоти — це масштабування виконує відеокарта.

Перед копіюванням `SDL_SetTextureColorMod` множить кольори текстури на яскравість, тобто застосовує затемнення з кроку 8 разом з «пульсуючим» освітленням `lightIntensity`, яке приходить з `Game::render`.

### Крок 10. Запасний варіант без текстури (рядки 133–159)

Якщо файлу `wall.png` чи `door.png` немає, гра не ламається, а малює стіну сама — піксель за пікселем. Базовий колір сірий для стін і коричневий для дверей. Вираз `((texX + texY) & 1)` створює шаховий візерунок: сусідні «цеглини» трохи світліші й темніші, тож стіна не виглядає пласкою. Кожен піксель затемнюється так само, як і текстура, і ставиться через `SDL_RenderDrawPoint`. Цей шлях значно повільніший, бо малює тисячі окремих точок замість однієї смужки.

## Частина 2. Монстри (спрайти)

Монстри — не частина карти, а окремі об'єкти з дробовими координатами. Їх малюють як **білборди**: пласкі картинки, які завжди повернуті обличчям до камери.

### Крок 11. Збирання й сортування (рядки 162–180)

```cpp
struct DrawMonster {
    float distance;
    float x;
    float y;
    const Monster* source;
};
std::vector<DrawMonster> drawMonsters;
drawMonsters.reserve(monsters.size());
for (const Monster& monster : monsters) {
    if (!monster.isAlive()) {
        continue;
    }
    const float dx = monster.getX() - playerX;
    const float dy = monster.getY() - playerY;
    drawMonsters.push_back({dx * dx + dy * dy, monster.getX(), monster.getY(), &monster});
}
std::sort(drawMonsters.begin(), drawMonsters.end(), [](const DrawMonster& a, const DrawMonster& b) {
    return a.distance > b.distance;
});
```

Спочатку складаємо список живих монстрів і для кожного рахуємо відстань до гравця. Береться **квадрат** відстані (`dx² + dy²`) без кореня: для порівняння «хто далі» корінь не потрібен, а без нього швидше. `reserve` заздалегідь виділяє пам'ять, щоб вектор не перевиділявся під час заповнення.

Потім список сортується **від найдальшого до найближчого**. Це «алгоритм художника»: як художник спершу малює фон, а потім передній план поверх нього, так і ми спершу малюємо далеких монстрів, а ближчі перекривають їх.

### Крок 12. Переведення в координати камери (рядки 182–190)

```cpp
const float spriteX = monster.x - playerX;
const float spriteY = monster.y - playerY;
const float invDet = 1.0F / (planeX * dirY - dirX * planeY);
const float transformX = invDet * (dirY * spriteX - dirX * spriteY);
const float transformY = invDet * (-planeY * spriteX + planeX * spriteY);
if (transformY <= 0.1F) {
    continue;
}
```

Спершу беремо позицію монстра відносно гравця. Але нам потрібно знати не «наскільки він на схід чи на північ», а «наскільки він попереду і наскільки ліворуч чи праворуч **від погляду гравця**». Для цього позицію переводять у систему координат камери, осі якої — площина камери і напрямок погляду. Математично це множення на матрицю, обернену до матриці `[plane | dir]`; `invDet` — це 1, поділена на її визначник.

У результаті:
- `transformY` — **глибина**: на скільки монстр попереду гравця вздовж погляду. Це та сама «перпендикулярна відстань», що й для стін, тому їх можна порівнювати.
- `transformX` — бокове зміщення: від'ємне — ліворуч, додатне — праворуч.

Якщо глибина менша за 0.1, монстр позаду гравця або впритул до камери — такого не малюємо.

### Крок 13. Розмір і місце на екрані (рядки 192–198)

```cpp
const int spriteScreenX = static_cast<int>((screenWidth * 0.5F) * (1.0F + transformX / transformY));
const int spriteHeight = std::abs(static_cast<int>(screenHeight / transformY));
const int spriteWidth = spriteHeight;
const int drawStartY = std::max(0, (screenHeight - spriteHeight) / 2);
const int drawEndY = std::min(screenHeight - 1, (screenHeight + spriteHeight) / 2);
const int drawStartX = std::max(0, spriteScreenX - spriteWidth / 2);
const int drawEndX = std::min(screenWidth - 1, spriteScreenX + spriteWidth / 2);
```

Горизонтальне положення монстра на екрані залежить від відношення бокового зміщення до глибини. Монстр точно попереду (`transformX = 0`) опиниться в центрі екрана; той самий боковий зсув на більшій відстані дає менший зсув на екрані — знову перспектива.

Висота спрайта рахується тією ж формулою, що й для стін: висота екрана, поділена на глибину. Ширина дорівнює висоті, тобто спрайт квадратний. Як і стіни, спрайт центрується по вертикалі й обрізається межами екрана.

### Крок 15. Малювання смугами з перевіркою глибини (рядки 219–229)

```cpp
for (int stripe = drawStartX; stripe <= drawEndX; ++stripe) {
    if (transformY >= depthBuffer[static_cast<std::size_t>(stripe)]) {
        continue;
    }

    const float normalizedX = static_cast<float>(stripe - drawStartX) / static_cast<float>(std::max(1, drawEndX - drawStartX));
    if (hasTexture) {
        const int srcX = std::clamp(static_cast<int>(normalizedX * static_cast<float>(texW - 1)), 0, texW - 1);
        SDL_Rect src{srcX, 0, 1, texH};
        SDL_Rect dst{stripe, drawStartY, 1, std::max(1, drawEndY - drawStartY + 1)};
        SDL_RenderCopy(renderer, monsterTexture, &src, &dst);
    }
```

Монстр малюється так само, як стіни, — вертикальними смужками по одному стовпцю екрана. Але перед кожною смужкою є важлива перевірка: ми порівнюємо глибину монстра з відстанню до стіни в цьому стовпці, яку записали в `depthBuffer` на кроці 5. Якщо стіна ближча, ця смужка монстра схована за стіною і її пропускаємо.

Саме завдяки цьому монстр, що визирає з-за рогу, видно лише частково: ті його смужки, де попереду є стіна, не малюються, а решта — малюються. Цей прийом називається **буфер глибини** (z-buffer), і тут він дуже простий — один масив на 800 чисел.

`normalizedX` показує, яка частина спрайта зараз малюється (0 — лівий край, 1 — правий). З нього обчислюється стовпчик текстури — точно як `wallX` для стін — і вертикальна смужка шириною 1 піксель розтягується на висоту спрайта.

### Крок 16. Монстр без текстури (рядки 230–257)

Якщо картинки монстра немає, він малюється вручну: для кожного пікселя смужки перевіряється, чи потрапляє він у коло (`radius2 > 0.24` означає «поза колом» — такі пікселі пропускаються, і там видно стіну позаду). Тіло червоне, у верхній частині посередині — світлі «очі», нижня частина трохи темніша. Як і для стін, це повільніший запасний шлях.

## Підсумок одним абзацом (для відповіді на захисті)

Для кожного з 800 стовпців екрана ми будуємо промінь з позиції гравця в межах кута огляду, використовуючи напрямок погляду і площину камери. Алгоритм DDA веде промінь від однієї лінії сітки до наступної, поки той не влучить у клітинку зі стіною. Ми обчислюємо перпендикулярну відстань до стіни (через це немає ефекту «риб'яче око»), ділимо на неї висоту екрана й отримуємо висоту вертикальної смужки. Точка влучання визначає, який стовпчик текстури намалювати, а відстань — наскільки його затемнити. Відстань у кожному стовпці записується в буфер глибини. Потім монстри сортуються від дальнього до ближнього, переводяться в координати камери, проєктуються на екран за тією ж формулою «висота / глибина» і малюються смугами — лише там, де вони ближче, ніж стіна в цьому стовпці.

## Як один стовпець отримує свій колір (пункт 6 з README у завданні)

Колір пікселя в стовпці `x` визначається так: промінь для цього стовпця знаходить найближчу стіну; якщо піксель вище або нижче смужки стіни — це небо або підлога (їх заливає `Game::render`); якщо всередині смужки — колір береться з текстури стіни або дверей у точці влучання і затемнюється залежно від відстані та боку грані; і нарешті, якщо в цьому стовпці є монстр, ближчий за стіну, поверх малюється відповідна смужка його спрайта.
